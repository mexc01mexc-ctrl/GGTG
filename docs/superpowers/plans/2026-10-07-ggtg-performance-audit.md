## 2. Что нашёл

### Главное (бьёт по всем)
1. **Список чатов перерисовывается ~30 раз в секунду.** В служебном чате «Telegram» код входа лежит под спойлером, и частицы спойлера анимируются прямо в превью списка. В каждом аккаунте фермы такие сообщения есть. Причина подтверждена счётчиком отрисовок: строка 8 (`Telegram`) - 268 перерисовок за 10 с; с выключенной анимацией спойлеров - 0. Код: `dialogs/ui/dialogs_layout.cpp`, `dialogs/ui/dialogs_message_view.cpp` (`pausedSpoiler`).
2. **Программа в 3 раза больше нужного**: в бинарник попадает таблица символов (593 МБ). Официальный `build.sh` делает `strip`, а наш DMG собирается вручную без него.
3. **ИИ-движок занимает лишний гигабайт**: `llama-server` по умолчанию создаёт 4 слота (`n_slots = 4`), хотя запросы идут строго по одному, и всегда грузит модуль зрения (0,9 ГБ), который нужен только для картинок.

### Данные и диск (растёт с размером баз)
4. **Каждая отправка переписывает весь реестр `sms_sent.json`** на главном потоке (`SaveSmsSentCache` в `SetSmsSendRecord`) и сразу оповещает все экраны. На реестре в десятки тысяч записей это мегабайты на каждое сообщение.
5. **«Главная» пересобирается на каждую строку журнала процесса** (`processes().changes()` срабатывает на каждую запись), и каждый раз читает весь `sms_attempts.jsonl` (до 8 МБ) и проходит по чатам всех аккаунтов (`FillReplies`).
6. **`FillReplies` для каждой попытки перебирает все аккаунты** (O(попытки × аккаунты)). «Результаты» читают и разбирают файл дважды (итог + A/B).
7. **Строка проверки в «Рассылке» раз в секунду** собирает получателей всех выбранных баз и считает статистику, даже когда ничего не менялось.
8. **Список баз**: каждая строка пересчитывает статистику на любое изменение баз, а счётчик «ответили» перечитывает всех пользователей всех баз при каждой перерисовке списка.
9. Мелкие постоянные таймеры: кнопка ИИ в чате (каждые 450 мс), менеджер аккаунтов (перерисовка всех строк каждые 2 с). Сами по себе дёшевы, но работают всегда.

### Работа и связи
10. **«Ответы» видят ответ, только если чат уже загружен** (`FindReplyText` смотрит загруженную историю). Новые ответы не ловятся сами - пользователь должен открыть чат.
11. **Две модели по 9B для разных задач**: перевод и помощник используют разные модели, а движок держит одну, поэтому при чередовании задач модель перезагружается (секунды задержки и 5 ГБ памяти туда-обратно).
12. Отладочные режимы (`GGTG_SNAPSHOT_DIR`, `GGTG_PAINT_STATS`, `GGTG_POWER_FLAGS`) стоят в боевом коде - убрать в конце работ.
13. 95 предупреждений компилятора в коде GGTG (в основном `&&` внутри `||` без скобок) - чистка.
14. **Android раздаётся отладочной сборкой** (`debuggable true`, без R8): медленнее и больше. Release-вариант с `minifyEnabled/shrinkResources` уже описан в gradle, нужен ключ подписи.
15. На Windows «осиротевший» движок после аварийного закрытия пока не гасится (на Mac сделано).

### Что с чем связано
```
Аккаунты (сессии, прокси-пул, спам-статус, счётчик за 24 ч)
   │  выбираются в: Рассылке, Накрутке, Экспорте, Сквидварде
   ▼
Сквидвард (бот, кэш пробивов) ──► Базы (index.json + файл на базу, имена)
                                     │
                                     ▼
Рассылка (форма, шаблоны, наборы) ──► Процесс (processes.json, ggtg.log)
   │                                  │
   ▼                                  ▼
реестр отправок sms_sent.json ◄── попытки sms_attempts.jsonl
   │                                  │
   └────────► Результаты / Ответы ◄───┘ (ответы: sms_replies.json, успехи)
                       │
                       ▼
             ИИ (профиль, агент, разбор, перевод) ── движок llama-server
Накрутка и Экспорт ни с чем, кроме аккаунтов и «Процессов», не связаны.
```

## 3. План (по этапам, от большего выигрыша к меньшему)

### Этап A. Быстрые большие выигрыши (низкий риск)
Статус: сделан 2026-10-07. Процессор в простое 20-30% -> 0,4%. Скрипт `make_dmg.sh` проверен (`--check`: бинарник 809 -> 248 МБ, приложение 269 МБ, подпись валидна, стрипнутая копия запускается). ИИ-движок: `-np 1` и модуль зрения только для запросов с картинками - собрано, в самом приложении не проверено (нужен живой запрос к ИИ).
- A1. Спойлеры в списке чатов - статичные. Цель: процессор в простое ≤ 1% вместо 20%. Проверка: счётчик отрисовок и `top`.
- A2. ИИ-движок: `-np 1`, модуль зрения подключать только для запросов с картинками. Цель: −1 ГБ памяти, та же скорость.
- A3. Скрипт сборки DMG `Telegram/build/ggtg/make_dmg.sh`: копия, `strip`, подпись, `hdiutil`. Цель: приложение ~270 МБ, DMG ~90 МБ.
- A4. «Главная»: пересборка не чаще раза в 2 с и только когда она открыта.

### Этап B. Данные без лишней работы
Статус: сделан 2026-10-07 (B1-B3; сборка и снимки проверены). B4 (таймеры кнопки ИИ и менеджера аккаунтов) не менял: замер показал, что они дёшевы. Не проверено под нагрузкой: реальная рассылка на большой базе.
- B1. Реестр отправок: запись на диск не чаще раза в 2 с (и при выходе), оповещение экранов одним пакетом.
- B2. Попытки рассылок: держать в памяти и перечитывать только при изменении файла; `FillReplies` через карту «id → аккаунт»; «Результаты» считают всё за один проход.
- B3. Строка проверки «Рассылки» и список баз - пересчёт по событиям, а не по таймеру; «ответили» по базе - из реестра (в нём уже есть id базы), без чтения всех пользователей.
- B4. Таймеры кнопки ИИ и менеджера аккаунтов - по событиям.

### Этап C. Надёжность и функции
Статус: сделан 2026-10-07 (C1-C3; C4 не делал: Windows не проверить). C1: входящие ответы ловятся на лету (`TrackManualSends` в `data/scraped_members_db.cpp`). C2: настройка `useTranslator` (по умолчанию включена только у тех, у кого переводчик уже скачан); без неё перевод идёт моделью для текстов, а «Установить всё нужное» не качает 5,4 ГБ. C3: реальных предупреждений было 6 уникальных (95 - повторы по файлам), поправлены главные; остались безобидные `lambda capture 'api'`. Не проверено вживую: приём входящего ответа (нужен живой собеседник) и скачивание без переводчика.
- C1. Ответы ловятся сами, по входящим сообщениям от тех, кому писали, - без открытия чатов; счётчик новых ответов на «Главной».
- C2. Одна модель для перевода в чате (Qwen3.5-9B), Index-Translate - только по желанию для массового перевода; кнопка «удалить неиспользуемые модели». Цель: меньше перезагрузок движка, −5,4 ГБ диска по желанию.
- C3. Чистка предупреждений компилятора в коде GGTG.
- C4. Windows: гашение «осиротевшего» движка (Job Object) - нужна проверка на Windows с вашей стороны.
